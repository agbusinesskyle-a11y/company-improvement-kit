# Employee-requested builds after owner approval

This reference describes the reusable execution process. It does not authorize
implementing a demonstration request. Check the current milestone and the
installation's private activation checkpoint before enabling execution. The
public preview supplies operating instructions, not a runtime or installer.

The selected native-bot connection is introduced in a separate
[step 5 handoff](bot-handoff.md). Its issue-and-receipt scope ends at readiness;
the broader execution sequence below applies only when separately supported and
explicitly authorized. An existing model-runner implementation is not evidence
that the native bot connection is installed or live.

## Bind the approval to future work

An operator may opt a new request into a build policy before planning starts.
Freeze its repository and exact base revision, allowed paths, executable checks,
model roles and permitted release destination into the planning package. Present
that scope clearly on the owner's decision card. One approval of that exact
package can authorize its stated build and release scope; an additional copied
planning approval is not inherently required.

A historical planning-only approval remains planning-only. Never attach execution
authority to its existing package or reuse its decision for a new version. Employee
text, a model response, an issue edit and an SMS reply cannot select a release
policy or extend the owner's approved scope.

## Keep project routes separate

The private coordinator supports a trusted runtime collection selected by exact
project key. An unknown project must fail; do not fall back to another lane.
Workers still receive one project and only their own role credentials. A native
issue runtime may bind an optional Linear project UUID as well as its team; freeze
that identity before planning and require it in create/recovery receipts. Existing
approvals keep their original identities when configuration changes.

Before enabling a business application, verify its own repository permissions,
base, bounded source context and isolated executable checks. A tiny practice
project's image, resource limits and path allowance do not prove compatibility
with a full application. Keep an unready profile disabled and report the specific
missing prerequisites. Respect protected model roles and production branch
triggers in that application's repository instructions.

## Execute and preserve evidence

After the verified owner decision, the process reserves the issue operation,
builds the approved requirements in an isolated checkout, checks the candidate,
and obtains an independent review. Preserve the approved package, issue identity,
exact candidate commit, executed check evidence and review result throughout.
Only an explicitly permitted release may follow. A successful command exit alone
is not deployment evidence. A build-and-review-only request must report that
result without claiming a release.

Use separate build, review and release workers with scoped credentials. Runnable
paths, test commands and provider destinations come from operator configuration.
The builder receives the frozen requirements as task data and cannot change
those trusted settings. Provider secrets stay outside model inputs and child
process environments.

A review requesting changes stops release. In-scope repairs remain bounded by
the original requirements and configured attempt limit, and every new candidate
requires fresh checks and review. Broader changes and exhausted repair attempts queue an honest source-thread
report and return to planning and a new owner decision. A failed report blocks
for operator recovery; it does not create an endless notification retry. Decline, cancellation and revision do not reuse old authority.

Reserve an operation durably before its effect. After a crash or uncertain
provider response, reconcile the original resource or process evidence; do not
blindly create another issue, launch another build, merge again, upload again or
repost the completion message. Preserve receipts for operations that already
started even if the request was subsequently cancelled.

## Connect reminders and source-thread status

An owner decision ends the pending approval reminder. SMS remains only an
attention notice linked to the decision surface. Report subsequent execution
status in the original authenticated request thread. Keep the reminder's delivery
binding and activation separate from build policy; configuring execution does not
activate SMS or rewrite historical routing and approval evidence.

## Activate only the verified installation

Before activation, publish the reusable skill checkpoint, bind the exact private
source and configuration, apply the documented migration, and verify compatible
worker roles and installed source. Give each worker durable private state storage;
an ephemeral working directory does not preserve restart receipts. Keep unsupported providers disabled. Distinguish
synthetic transport/process tests from live model execution, provider access and
verified deployment. Preserve completed proofs rather than replaying them merely
because a new component was added.

## Current private runtime limits

The connected candidate uses Linear, native Grok through Ringer, a separate reviewer,
Railway receipt reconciliation and Slack thread reporting. It does not compose a
GitHub merge. Build, review and release share a durable candidate artifact directory
on the execution host; automatic cross-host transfer is unavailable. A continuous
worker is disabled by default and loads no configuration or credentials until
explicitly enabled. Graceful shutdown finishes the bounded current cycle; a hard
interruption relies on the permanent reservation and recovery record.

Live activation and installation-specific verification remain pending. Upstream
planning, package review and public publication continue through their existing
operator procedures. This source milestone does not make the entire workflow
unattended or independently installable.

For the supported release CLI, tracked custom ignore files, tracked dependency
folders that the CLI always excludes, symlinks and submodules are rejected before
upload. Verify that the execution host has no effective external Git exclusions
and that staging is outside a parent Git repository before activation. That host
prerequisite is operator-verified; the candidate does not automate it. A passing
source test is not evidence that an arbitrary installation satisfies it.
