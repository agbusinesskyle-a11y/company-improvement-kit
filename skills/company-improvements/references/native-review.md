# Native review and draft pull requests

The private implementation provides a new opt-in `issue_handoff_build_review`
scope. It extends the native path through independent review, bounded repairs and
a draft GitHub pull request, followed by the existing outcome-message outbox.
Source tests use disposable databases and Git with synthetic model/provider
responses. A private marker-only live practice chain is verified with a recorded operator
continuation after a CLI status-code defect; this is not real-app or unattended
repair-loop certification. This public kit remains a
skill/documentation preview without a runtime or installer.

## Before a future approval

Keep the native build fields and release authorization false. Freeze a separate
`review_worker_id`, `publisher_worker_id`, exact requested/reported reviewer model,
`review_limits` and `pull_request_base_branch`. Builder, reviewer and publisher IDs
must differ. The existing repair ceiling is frozen into the package; default two
repairs after the initial draft. Model time is bounded to 600 seconds and accepted
output to 16,384 tokens; this is not a prepaid cost cap.

Publish the generic snapshot and bind its commit to the exact private package
using [approval checkpoints](approval-checkpoints.md). Obtain an owner decision
covering this expanded scope before execution. Existing handoff-only or checked-
build approvals retain their original stopping points. Configuration changes,
issue edits and this documentation never extend them.

## Connected behavior

1. The builder creates a checked draft under the approved base and paths.
2. A separate native model session reviews the exact plan, allowed text, diff and
   accepted check evidence. It has no edit, shell, publishing or release tools.
3. Concrete in-scope findings return to the builder. Each repaired candidate gets
   its own checks and fresh review. New scope or exhausted repairs stops for
   owner revision and produces no pull request.
4. An accepted review allows a deterministic publisher to create one new feature
   branch and one draft pull request. It binds the exact repository, candidate,
   original base, review and package. Existing branches cannot be replaced.
5. The existing status worker delivers the verified PR URL to the source thread,
   owner thread and existing issue. Completion means a reviewable draft, not a
   merged or released application.

Independent means a separate role, context and session; it does not necessarily
mean another vendor. There is no Ringer fallback. Every candidate blob is hashed,
including unchanged binary assets. Text context is limited to the approved paths
and 1 MiB; the full tree is capped at 50 MiB/10,000 entries. Larger changes need a
smaller approved package. Model review is not a formal correctness guarantee.

## Installation and recovery

Install the matching private worker package on the existing execution host.
Provision distinct coordinator grants for review and completion. The publisher
needs a repository-scoped GitHub credential; the reviewer uses existing native
model authentication. Keep credentials outside plans, prompts and this public kit.
Append review and publication pickups to the existing locked host cycle rather
than adding another timer. Repairs run in later cycles. A successful issue that returns `executing` must
exit successfully so the host can continue to handoff. The private CLI now handles
that status; never recreate the issue to work around an exit-code failure. Credentials, candidate paths and a new exact approval remain installation-specific.
Keep the expanded cycle disabled until its required credentials are available.
Once access is verified, enable the existing cycle and observe one idle pickup
before presenting the new approval. Empty queues allow this readiness check
without starting a build. Track credential expiry in private installation records;
credential renewal never extends the approved execution scope.
Give the publisher credential only to the publishing process, not model contexts.
Verify repository access, the exact base reference and branch-triggered automation
without a test push or test PR. Use the existing lock and timer; an authenticated
empty queue proves access only, not a completed build or publication.

A preparatory plan-review response may be retained when a local acceptance budget
rejects it. Preserve the original failure and actual usage. An operator may
explicitly assess that existing planning response without another model call;
record any local budget exception and never alter frozen build/review limits or
treat it as an owner decision. This does not authorize runtime budget overrides.

A permanent journal precedes each model, push and PR dispatch. Recovery reads
retained candidate/review evidence and exact provider state. A lost response never
causes an automatic second model run, push or PR create. The original worker may
reconcile after lease expiry; cancellation and profile drift still stop progress.
A pushed branch without a recorded PR dispatch remains uncertain for operator
handling. Do not delete journals to force retries.

There is no merge, release, preview, automatic branch cleanup or cross-host
candidate transfer. GitHub workflow-file edits require separate scope. Verify that
existing repository automation will not independently deploy a new feature branch.
The public clean-install and expanded live employee-request proofs remain pending.
